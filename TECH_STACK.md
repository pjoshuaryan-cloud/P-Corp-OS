# Tech Stack

**Status:** Skeleton — UI shell platform, backend language, IPC mechanism, process lifecycle, packaging, database, and sync are decided; auth and iOS companion specifics are still open.

## Purpose

Record the technology choices for each layer, with the trade-offs that justified them — not just the final pick.

## Decided (from FOUNDER_BRIEF.md)

- Primary experience is a desktop application, not a web application.
- Mobile is a companion app, not the primary surface.

## Decided (2026-07-20)

- **Platform scope: Apple-only.** Desktop is macOS; mobile companion is iOS. No Windows/Linux requirement — this is a deliberate choice, not an oversight, and should be revisited explicitly (not silently) if that ever changes (e.g. if Nick, Raoof, or a future hire need non-Apple access).
- **Desktop UI shell: native SwiftUI.** Chosen over Electron and Tauri. Rationale: (1) highest ceiling for the "headquarters, not an app" feel the Founder Brief calls for — real menu bar integration, native notifications, OS keychain, Spotlight-style quick actions; (2) SwiftUI is Apple's shared UI framework across macOS and iOS, so the iOS companion app can reuse real code and patterns from the desktop shell rather than being a fully separate build — this is the most direct way to satisfy "one Frank, seamless across devices" at the UI layer. Electron was ruled out once cross-platform reach stopped being a requirement (its main advantage), leaving it the heaviest option for no corresponding benefit. Tauri remains a credible fallback if a strong reason emerges to keep the UI layer in TypeScript instead of Swift, but was not chosen because it forces a second, separate mobile codebase.
- **Frank's intelligence layer runs as a separate local service**, not inside the SwiftUI app itself, communicating with the UI shell over local IPC. This decouples Frank/agent logic from the UI framework choice.
- **Backend language: Python**, via the Claude Agent SDK. Rationale: Trading Division is the flagged likely first real specialized agent (`ROADMAP.md` → Phase 3, `TRADING_DIVISION.md`), and the existing trading-robot repo's analysis/backtesting/statistics tooling is already Python (135 Python files vs. 19 MQL5 files, confirmed 2026-07-20) — the EA itself is MQL5, but every layer of walkforward/edge validation on top of it is Python. Building Frank's backend in Python means direct reuse of, and familiarity with, that existing tooling, rather than a second implementation or a cross-language shell-out. TypeScript's main advantage (sharing a language with the UI shell) no longer applies now that the shell is native Swift; its remaining edge (event-loop concurrency) is a theoretical advantage for a personal assistant's load, not a concrete one, and doesn't outweigh the Trading Division fit.
- **IPC mechanism: local HTTP + WebSocket, served by the Python backend (FastAPI), bound strictly to `127.0.0.1` with a local auth token.** REST endpoints handle simple request/response calls; a WebSocket connection carries streaming Frank responses (token-by-token) and unprompted push notifications from Frank to the UI (serving Layer 1's "Notifications" responsibility). Chosen over XPC, a raw Unix domain socket, and gRPC because it's the only option that is simultaneously (a) native to Python's ecosystem, (b) capable of real streaming and server-initiated push, and (c) the *same interface* that can later be exposed for remote/mobile access — bound to a real network address behind proper auth and TLS instead of loopback — rather than a separate integration. XPC and Unix sockets were ruled out specifically because they're local-only by design and would have to be rebuilt once iOS/remote sync (per FOUNDER_BRIEF.md → Platforms) becomes real; gRPC was ruled out because maintaining protobuf schemas across Swift and Python is ongoing overhead this scale doesn't justify.
- **Process lifecycle: target architecture is a persistent background service, managed via `SMAppService`** (Apple's ServiceManagement framework, macOS 13+ — the correct modern primitive for an app-shipped login-item background helper, not a hand-rolled `launchd` plist). Rationale: a backend that only runs while the SwiftUI app is open contradicts the brief's own framing of Frank as an always-available second brain with real "Notifications" responsibility (Layer 1) and background agent work (e.g. an unattended trading analysis) — and gives an eventual iOS companion nothing to talk to unless the Mac app happens to be open in the foreground. Sequencing: early prototyping can run the backend as a simple spawned subprocess for faster dev iteration (no daemon-reload cycle while there's nothing real to test yet); graduate to the `SMAppService`-managed persistent service once the backend is stable enough to be worth installing as a standing process. This is a phasing detail, not a contradiction of the target.
- **Packaging: embed a self-contained, relocatable Python runtime + locked dependencies as bundled app resources, launched via a thin native (Swift/C) shim executable** — not a PyInstaller/py2app frozen single-binary. The shim's only job is to resolve the bundle-relative interpreter path, set `PYTHONHOME`, and exec the Python entrypoint; it's what `SMAppService` actually registers as the LaunchAgent target, and it's trivial to sign. Rationale: PyInstaller/py2app-style freezing gets more fragile as dependencies grow, specifically because macOS notarization requires every bundled `.dylib` to be individually signed — a real cost once Trading Division's likely numpy/pandas dependencies (and whatever later agents need) are in the mix. Owning the embedding directly avoids inheriting a third-party freezing tool's quirks over a decade-long horizon, at the cost of a small amount of upfront native-launcher plumbing. Natural tooling pairing: a relocatable standalone build (e.g. `python-build-standalone`) plus `uv` for a locked, reproducible dependency set — not a separate decision, just the obvious default. Adjacent but explicitly not resolved here: codesigning/notarization strategy for a persistent, network-listening background service — flagged as a future `SECURITY.md` item, not a fork in this decision.
- **Database: SQLite, embedded locally in the Python backend**, as the primary store for tasks, projects, conversations, and memory records (structured data via normal tables/relations, flexible-schema fields via SQLite's JSON columns — one engine for both, not two). A semantic/vector search layer (e.g. `sqlite-vec` or a small embedded vector index) sits on top for contextual memory recall, rather than a dedicated vector database serving as the primary store — vector DBs are a poor fit for the relational needs of tasks/projects (status, due dates, ownership). Rationale: zero ops overhead, mature tooling in both Python (stdlib) and Swift (GRDB/SQLite.swift), fits the local-first reality of a backend that already runs on-device via `SMAppService`. Chosen over Postgres specifically to avoid forcing the still-open self-hosted-vs-cloud sync question today — Postgres would require deciding where it's hosted before there's a second device to justify the complexity. SQLite doesn't foreclose that answer: it can stay purely local indefinitely, or later pair with a sync layer (e.g. libSQL/Turso's SQLite-compatible embedded-replica model) without a storage-engine migration.

- **Backend/sync: libSQL, via its server component `sqld`, starting on Turso's managed offering** — not a hard self-hosted-vs-managed fork. Rationale: `sqld` is purpose-built for exactly this shape of problem — a local SQLite database (already decided) that syncs as an "embedded replica" against a remote counterpart while remaining fully functional if disconnected. Critically, `sqld` is open source and speaks the same protocol whether it's Turso's managed offering or a self-hosted instance Joshua runs himself — so "who hosts it" becomes a reversible operational choice made later, not a decision locked in today. Chosen over (a) a pure Mac-as-server model reached via a private tunnel (e.g. Tailscale), ruled out because Frank would only be reachable when the Mac is awake and connected — a real failure mode for a phone-only, away-from-desk scenario, not an edge case; and (b) committing to full self-hosting now, which would mean Joshua personally owning security/patching/backups for an internet-exposed personal-data server on top of the trading robot and Alpha Mode already competing for his time. Sequencing: start on managed Turso now for low ops overhead while the trading robot stays the priority; migrate to self-hosted `sqld` later if full data sovereignty for the most sensitive memory categories comes to outweigh convenience — no data-model or protocol rewrite required, just relocating the same server. Flagged for `SECURITY.md`: the most sensitive memory categories (marriage, family, health) should be end-to-end encrypted before leaving the device, so even the managed-Turso period never exposes plaintext to a third party.

- iOS companion specifics: how much of the SwiftUI desktop code is literally shared vs. adapted per-platform (this is a real question even with SwiftUI — "shared framework" isn't "zero mobile-specific work").
