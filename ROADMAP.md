# Roadmap

**Status:** Active — Phase 1 underway as of 2026-07-20.

## Purpose

Sequence the work so P Corp OS gets built "slowly, correctly, layer by layer" without stalling or getting rushed — per FOUNDER_BRIEF.md → Development Philosophy.

## Phases

**Phase 0 — Foundations. Complete as of 2026-07-20.** Documentation and repo structure (this repo), `TECH_STACK.md`'s full decision set, and `ENGINEERING_MANUAL.md`. No production code was written, per the brief's own instruction. Trading robot remained the active priority throughout.

**Phase 1 — The interview. In progress, started 2026-07-20.** Multi-session process where Frank (via Claude) interviews Joshua to build a mental model of his personality, communication, decision-making, values, goals, risk tolerance, etc. (full list in FOUNDER_BRIEF.md → Before Frank Exists). This happens before any Layer 2 code, not alongside it. Open thread within this phase: how interview content gets recorded, especially for sensitive categories (marriage, health, finances) — flagged in `MEMORY_SYSTEM.md`/`SECURITY.md` as needing privacy handling that doesn't exist yet, so nothing sensitive is being committed to this repo verbatim until that's resolved with Joshua directly.

**Phase 2 — Platform layer (Layer 1). Started 2026-07-23.** Build the minimum P Corp OS platform needed to support one real use case end to end.

Begun with the desktop UI shell — a static SwiftUI layout (sidebar, War Room center, right rail), per Joshua's own phased UI plan (visual shell first, interactivity and intelligence layered in afterward). By 2026-07-24 the shell had grown well past static: real navigation, dark mode, a working particle-based presence for Frank, keyboard shortcuts, an app icon, and the visual/logo work all landed — see `UI_GUIDELINES.md` for the full decision log.

**Backend started 2026-07-24.** First real Python service (`backend/`, FastAPI via `uv`) proving the IPC contract decided in `TECH_STACK.md` — a `/health` endpoint and a `/ws` WebSocket that streams responses back — and the SwiftUI shell's "Talk to Frank" input is now genuinely wired to it. Started echo-first to prove the IPC plumbing independent of LLM complexity, then upgraded the same day to real Claude reasoning: the plain `anthropic` SDK (not the Agent SDK — see `TECH_STACK.md` for why), a real system prompt distilled from `PERSONALITY_SPEC.md` (`backend/app/personality.py`), and conversation persistence in SQLite (`backend/app/db.py`) — one continuous conversation, loaded from disk on connect, matching "there is only ever one Frank." **Verified end-to-end 2026-07-24**, sooner than the "next week" originally planned: Joshua added a real Anthropic API key to `backend/.env`, and the full path — SwiftUI "Talk to Frank" input → WebSocket → Python backend → real Claude reasoning → streamed response back into the UI, with SQLite persistence confirmed across separate connections — genuinely works. First real conversation with Frank in the project's history.

**Typed memory records, same day.** `MEMORY_SYSTEM.md` — previously a stub — now has a working first layer: durable facts/context (`backend/app/memory.py`, `backend/app/db.py`), separate from raw conversation history, reusing the existing Claude Code memory scheme's four types. Frank's first tool call: one hardcoded `save_memory` tool, deliberately distinct from (and much smaller-risk than) the deferred Agent SDK. Verified: Frank saved a real memory mid-conversation, and a fresh connection recalled it unprompted.

**Memory made visible, same day.** One of the shell's 9 placeholder sections ("Frank") is now real — a read-only view of everything in `memory_records`, backed by a new `GET /memory` endpoint. Closes the loop: memory isn't just something Frank privately writes to disk anymore, Joshua can actually see what's been remembered.

The full per-device-keypair auth and `SMAppService` packaging haven't been started — flagged as explicit next steps, not forgotten. Real *agentic* Frank (general tool-use, the Agent SDK) is still Phase 3, gated on `SECURITY.md`'s permission model.

**Phase 3 — Frank (Layer 2) + first agent (Layer 3).** Stand up Frank against one real, low-risk agent rather than all twelve at once. Candidate: a read-only Trading Division assistant, since that domain is already deeply understood (see `TRADING_DIVISION.md`).

**Phase 4+ — Expand agents, deepen Alpha Mode and Trading Division integration, build out desktop War Room UX.** Order not yet decided — depends on what Phase 3 reveals.

## Explicitly not decided

- No calendar dates. The brief is explicit about not rushing; a roadmap with dates on a 10-year platform would be exactly the kind of speculative fiction the founder brief warns against.

**Real macOS notifications, 2026-07-25/26.** Closes Layer 1's "Notifications" responsibility (`FOUNDER_BRIEF.md`) — `TECH_STACK.md` had already decided the mechanism (WebSocket carries unprompted pushes from Frank), this just built it. `UNUserNotificationCenter` hard-crashes on this still-unbundled app; fell back to `osascript`, which doesn't need a real bundle identity. Also surfaced a process lesson: running raw test scripts directly against the live backend (same database real conversations live in) can shift which conversation is "active" without meaning to — nothing was lost, but worth care going forward.

**Forgetting/versioning for memory records, 2026-07-26.** Closes `MEMORY_SYSTEM.md`'s flagged gap — `memory_records` only ever accumulated before this, no update or delete existed. Soft-delete (`deleted_at`), not a real DELETE, keeping it reversible and matching `SECURITY.md`'s "regular" tier for both memory tools. Two paths, one mechanism: Frank's new `forget_memory` tool (matches by title) and a manual trash icon in `FrankView`. "Versioning" is deliberately forget-then-resave, not a version-history schema. Verified end-to-end both ways, then confirmed live — Joshua used the actual trash icon to forget a real memory himself.

**Calendar section built, 2026-07-26** — the first of the 8 remaining placeholder nav sections to become real. Picked deliberately over the other 7: Trading Division is blocked by `TRADING_DIVISION.md`'s own sequencing, Alpha Mode Media/Finance/Personal all need external data sources or touch unresolved sensitivity questions, Agents/Automations are UI for Phase 3 capabilities that don't exist yet — Calendar needed none of that, just real local macOS data. `EventKit` silently failed (no permission dialog ever appeared, confirmed with a standalone test) — same root cause as the earlier `UNUserNotificationCenter` crash, this app still has no real bundle. Fell back to AppleScript (`SystemCalendar.swift`), same pattern as notifications. Real events now show in a new `CalendarView` and in the War Room right rail's "Today's Agenda" card (the old hardcoded placeholder data removed entirely).

**Knowledge section built, 2026-07-26** — second of the 8 placeholder sections. Deliberately not a generic file browser: a real doc viewer for this project's own foundational markdown files (`FOUNDER_BRIEF.md`, `ROADMAP.md`, `TECH_STACK.md`, etc.) — Frank's own knowledge starts with the documents that define him. Read directly off disk, no backend involvement. A small hand-rolled markdown renderer (`SimpleMarkdownView`), scoped to exactly what these docs use (headings, lists, inline bold/italic/links) rather than a third-party package.

**`SMAppService` packaging, stage 1 done — a real `.app` bundle, 2026-07-26.** None of the remaining 6 placeholder sections had as clean a "ready now" angle as Calendar/Knowledge did (real external dependencies, unresolved sensitivity questions, or Phase 3 prerequisites), so asked directly and picked this instead. `desktop/build_app.sh` now assembles and ad-hoc signs a real bundle — three real problems found and fixed along the way (not guessed around): codesign rejecting SPM's own resource-bundle placement, stray resource-fork extended attributes on source artwork, and — the more consequential one — a properly-launched bundle's working directory is `/`, not `desktop/`, silently breaking every cwd-relative path (`AuthToken.swift`, `KnowledgeDocs.swift`) the raw-executable era had assumed; fixed via `ProjectPaths.swift` deriving the repo root from `#filePath` instead, independent of runtime cwd. Also confirmed directly: a real signed bundle gets normal Dock/activation behavior automatically — the manual workaround for the raw executable is provably no longer needed for this launch path, though it stays in place since `swift run` remains the everyday dev workflow. Verified live by Joshua: Dock icon appeared immediately, shortcuts and all sections work through the real bundle. Stages 2 (embed Python + a native shim) and 3 (register via `SMAppService`) are separate, not started.

**`SMAppService` packaging, stage 2 done — the Python runtime is embedded, 2026-07-28.** `desktop/build_app.sh` now downloads a relocatable CPython 3.12.13 build (python-build-standalone), installs the exact locked backend dependencies into it, compiles a thin native C shim (`backend_shim.c`), and embeds both in the real bundle — decoupling from this dev machine's own `uv`-managed venv and system Python, the actual point of this stage. Deliberate scope call: the shim's `PYTHONPATH` still points at the real repo's `backend/` source rather than a bundled copy, since `db.py`'s SQLite path is relative to its own file location — bundling a copy would silently fork Frank's memory into a second database depending on launch method, breaking "there is only ever one Frank." Real bug found and fixed along the way: `load_dotenv()` searches from the process's working directory by default, not the file's own location — since the shim can launch from anywhere, this silently left the API key unset the first time a real conversation was attempted through it; fixed the same way stage 1's cwd bug was, deriving the path from `__file__` instead. Verified with escalating real tests: the runtime survives being moved to a different path, the real backend module imports and serves `/health` through it standalone, then a genuine live Claude conversation end-to-end through the actual signed bundle. Stage 3 (registering the shim via `SMAppService` as a persistent LaunchAgent) is separate, not started — the shim still needs manual launching for now.

**`SMAppService` packaging, stage 3 done — Frank is a real persistent background service, 2026-07-28. This closes out `TECH_STACK.md`'s full 3-stage packaging plan.** `BackendService.swift` wraps `SMAppService.agent(plistName:)`, wired to the existing (previously stubbed, no-op) "Launch at Login" toggle in Settings. Real bug found via the actual unified system log (not the shell-builtin `log` that was silently shadowing `/usr/bin/log` and swallowing predicates): the LaunchAgent registered and was approved cleanly, but never actually started — `launchd`'s `posix_spawn` was failing with ENOENT because the plist's `ProgramArguments[0]` was just the bare executable name, and `SMAppService`/BTM does not rewrite that to be bundle-relative before handing it to `launchd`, contrary to what the API's framing implied. A real runaway respawn loop (retrying every ~10s against the broken config) was caught and stopped via `launchctl bootout` before it caused any problem. Fixed with the executable's real absolute path. **Verified thoroughly, not just "it registered":** killed the backend process directly and confirmed `launchd`/`KeepAlive` restarted it automatically within seconds; quit the GUI app entirely and confirmed the backend kept serving real requests regardless — genuine independence, the actual point of this whole 3-stage effort, not just a process that happened to be running.

**Push-to-talk voice input, 2026-07-28.** Finally scoped and built the original ask (particle blob hidden while texting, present and voice-reactive while talking) — properly scoped as its own dedicated piece of work, not bolted onto something else, per the earlier deferral. Confirmed decision: push-to-talk, not continuous/always-listening — smaller privacy footprint, no wake-word/VAD complexity. `VoiceInput.swift` uses `Speech`/`AVAudioEngine` directly — privacy-gated frameworks in the same category as `EventKit`, which failed outright pre-packaging; worth trying specifically because `SMAppService` packaging now gives the app a real signed bundle. `FrankOrb` takes a real, optional live audio level (mic RMS) blended with its existing synthetic shimmer, and reappears specifically while listening regardless of an active text thread — directly closing the original visual ask. Real bug found through live testing: the first version's `stop()` cancelled the recognition task immediately, truncating real speech (confirmed: a full sentence collapsed to "And it's so") — fixed by waiting for the recognizer's own final callback instead of assuming the click itself delivers the result. Retested with a complete sentence afterward and confirmed clean. Text-to-speech (Frank's replies spoken aloud) is a separate, later stage — this is voice input only.

**Full searchable, date-grouped conversation history, 2026-07-28.** Direct response to Joshua wanting Frank to remember all chats indefinitely and be able to reopen any of them. Retention was already indefinite — no expiry logic anywhere in `db.py`, confirmed by inspection rather than assumed — so the actual gap was findability, not persistence: the existing conversation switcher was a small flat list with no way to search or see when something last happened. `list_conversations` (`backend/app/db.py`) now computes `last_message_at` per conversation (`MAX(messages.created_at)`) and sorts by it instead of creation order, and accepts an optional `q` param doing a real `LIKE` search across every message's content, not just the first-message preview — exposed via `GET /conversations?q=`. `ConversationListPopover` (`WarRoomView.swift`) rewritten in place (not a new UI) with a debounced search field and sections grouped by day ("Today", "Yesterday", "Sunday, Jul 26", ...). Real bug hit and fixed along the way: the persistent `SMAppService`-managed backend doesn't hot-reload Python source changes, so it kept serving stale responses (missing `last_message_at`, ignoring `q`) until `launchctl kickstart -k` forced a restart — worth remembering now that Frank runs as a real background service rather than something restarted by hand on every edit. Verified live: search for "Joshx" correctly isolated the one matching conversation among several, with correct day-grouped labels.

**Text-to-speech, auto-stop voice input, fresh conversation per launch, 2026-07-28.** Three direct pieces of feedback from actually using push-to-talk and the conversation history feature, all fixed same day. (1) Frank now speaks replies aloud via on-device `AVSpeechSynthesizer` (`VoiceOutput.swift`) — only for turns that started as voice input, never for typed ones — played through a real `AVAudioEngine` graph specifically so the PCM buffers could be RMS-analyzed and fed into `FrankOrb`'s shimmer, closing the audio-reactive-output requirement `UI_GUIDELINES.md` had flagged as unbuildable until real voice existed. Voice selection filters for `gender == .male` before ranking by quality — the first version ignored gender entirely and silently picked a female system default; confirmed live after Joshua downloaded a real Enhanced/Premium male voice via System Settings' Read & Speak pane (the actual fix for "too robotic" — no installed voice on this Mac was above default quality, a ceiling no selection logic alone could fix). (2) Push-to-talk no longer needs a second click to end a turn — `VoiceInput.swift` auto-stops once real speech has been detected and then gone quiet for ~1.2s, with a 60s safety cap and manual click-to-stop kept as an early-exit option. (3) A brand-new conversation now starts automatically once per app launch (`BackendClient.swift`) rather than resuming whatever was last active — old ones don't just sit there, they stay fully reachable through the search/date-grouped history browser. Implemented as a `static`, not instance, flag specifically because War Room's view (and its `BackendClient`) gets recreated on every sidebar navigation, not just on launch — an instance-level flag would have wiped an in-progress conversation just from clicking to Settings and back. All three verified live by Joshua directly.
